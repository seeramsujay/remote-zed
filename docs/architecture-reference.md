# **Architecture for Remote Interception and Mobile Control of Zed Editor via the Agent Client Protocol**

## **Architectural Foundations and Interception Mechanics**

Remote interaction with desktop-bound code editors requires decoupling interface rendering from background reasoning runtimes1. Modern open-source development environments, specifically the Rust-native Zed editor, rely on structured protocols to separate editor user interfaces from external artificial intelligence agents1. The central framework enabling this integration is the Agent Client Protocol (ACP), an open standard introduced by Zed Industries that standardizes communication between editors and autonomous coding agents over standard input and output (stdin/stdout) streams or network sockets using JSON-RPC 2.01.  
When an agent such as AntiGravity connects to Zed, the editor launches the agent executable as an independent child process1. Zed communicates with this subprocess by piping structured JSON-RPC messages1. Because ACP operates over standard IPC channels, an intermediate software layer can intercept, monitor, and inject messages into the stream without modifying the core editor source code or the agent binary6. This proxy mechanism allows a secondary interface, such as a remote mobile application, to mirror the primary chat stream, issue new agent prompts, authorize system actions, and execute system commands asynchronously1.  
Achieving complete remote control over a host machine left in a hostel or remote location requires isolating core operational capabilities rather than streaming a raw graphical desktop4. Mobile form factors are poorly suited for dense code-editing surfaces, but excel at processing streaming conversational interfaces, reviewing structural code diffs, approving tool execution requests, and executing version control actions1. By capturing the bidirectional ACP message flow between Zed and the AntiGravity agent, a headless host daemon can bridge local IPC streams to a secure network transport, making the full agent session accessible to a mobile application4.

| Protocol Standard | Primary Operational Purpose | Underlying Transport Mechanism | Functional Scope in Architecture |
| :---- | :---- | :---- | :---- |
| **Agent Client Protocol (ACP)** \[cite: 1, 11\] | Standardizes AI agent integration with code editors1. | JSON-RPC 2.0 over stdin/stdout, WebSockets, or SSE1. | Session management, prompt turns, streaming token updates, tool approval requests1. |
| **Model Context Protocol (MCP)** \[cite: 1, 14\] | Standardizes agent access to external data sources and tools11. | Local stdio pipes or remote HTTP/OAuth endpoints forwarded over ACP1. | Database inspection, external search tools, context indexing, file-system servers1. |
| **Language Server Protocol (LSP)** \[cite: 1\] | Standardizes static code intelligence for editors1. | JSON-RPC 2.0 over standard input/output pipes1. | Syntax parsing, diagnostics, code completion, symbol definitions. |

The relationship between these protocols establishes a layered stack where ACP handles editor-to-agent interactions, while MCP supplies underlying data tools to the agent1. Intercepting the ACP layer captures both the high-level reasoning generated by AntiGravity and the tool calls dispatched to the underlying operating system1. This structural decoupling allows a custom host daemon to function as an transparent proxy, granting mobile clients full parity over agent chat turns and system command execution7.

## **Host Daemon Architecture and Bridge Engine**

The host infrastructure requires a lightweight, high-performance system daemon written in Rust to run on the host laptop. Rust offers zero-cost abstractions, memory safety, and native asynchronous I/O through the Tokio runtime, making it optimal for intercepting standard I/O streams with minimal latency16. The daemon, designated zed-remote-daemon, serves a dual operational role: it acts as a transparent process stdio proxy when Zed is running locally, and functions as an independent remote control host when accessed out-of-band from a smartphone1.  
The process interception model works by substituting the AntiGravity binary path in Zed's configuration with the zed-remote-daemon binary path5. When Zed starts an agent session, it invokes the daemon5. The daemon immediately spawns the real AntiGravity executable as its own child process, establishing bidirectional asynchronous pipes (tokio::process::ChildStdin and tokio::process::ChildStdout)17. Messages sent from Zed to AntiGravity, and responses returned from AntiGravity to Zed, pass through an internal message router inside the daemon7.

JSON  
{  
  "agent\_servers": {  
    "AntiGravity-Remote": {  
      "type": "custom",  
      "command": "/usr/local/bin/zed-remote-daemon",  
      "args": \[  
        "--target-command", "/usr/local/bin/antigravity",  
        "--target-args", "acp",  
        "--port", "8443"  
      \],  
      "env": {  
        "RUST\_LOG": "info"  
      }  
    }  
  }  
}

The daemon deserializes incoming Newline-Delimited JSON (NDJSON) frames into typed structures using serde\_json7. Frames containing prompt requests (session/prompt), streaming message updates (session/update), and tool authorization prompts (session/request\_permission) are published to an internal broadcast channel (tokio::sync::broadcast)7. This broadcast channel mirrors every message to an active WebSocket server thread bound to a secure private network interface4.  
Beyond message proxying, the host daemon incorporates a dedicated system and version control execution engine16. To allow remote users to stage, commit, and push Git changes without opening a code editor canvas, the daemon exposes explicit RPC methods that invoke local system binaries or interface directly with the libgit2 C library via Rust bindings (git2 crate)16. System control routines, such as retrieving CPU and memory telemetry or triggering power state changes (such as entering sleep mode or shutting down), are handled via native system calls (systemctl, shutdown, or osascript) executed through std::process::Command17.

| Daemon Module | Underlying Rust Crates | Core System Functionality |
| :---- | :---- | :---- |
| **Async Process Proxy** | tokio (v1.x), tokio-util \[cite: 16, 17\] | Spawns child agent processes, pipes stdin/stdout, handles asynchronous stream splitting17. |
| **Protocol Serialization** | serde, serde\_json \[cite: 7\] | Deserializes JSON-RPC 2.0 frames, inspects method signatures, serializes outbound events7. |
| **Network Gateway** | tokio-tungstenite, rustls \[cite: 9\] | Manages encrypted WebSocket servers over private IP overlay networks9. |
| **Version Control Engine** | git2, std::process::Command \[cite: 16, 17, 19\] | Performs file staging (git add), commit creation (git commit), and remote repository sync (git push)19. |
| **System Diagnostics** | sysinfo, libc | Monitors CPU/RAM utilization, tracks battery status, and manages OS process termination17. |

Network security is established without exposing public ports to the open internet9. The daemon binds its WebSocket server exclusively to a WireGuard-based private mesh network address (such as Tailscale)9. Transport Layer Security (TLS) is enforced using self-signed or private network certificates via rustls, and incoming WebSocket handshake requests must present a pre-shared cryptographically secure JSON Web Token (JWT)9. This ensures that even on insecure hostel networks, the desktop remains completely isolated from unauthorized external access9.

## **Mobile Client Architecture and Flutter Implementation**

The mobile interface is designed specifically for target interaction rather than full workspace management. Built using the Flutter framework, the application utilizes a dual-panel layout optimized for smartphones: a Primary Session Panel dedicated to real-time AI Agent interaction, and a System Control & Repository Panel dedicated to Git operations and hardware management.  
Integration with the Agent Client Protocol on mobile is established using the acp\_dart package, a Dart implementation of the ACP specification7. The package provides connection adapters (ClientSideConnection and AcpStream) that convert raw WebSocket streams into typed Dart objects matching the official ACP schema7.

Dart  
import 'package:acp\_dart/acp\_dart.dart';  
import 'package:web\_socket\_channel/web\_socket\_channel.dart';

class RemoteAgentService {  
  late ClientSideConnection \_client;  
  final WebSocketChannel \_channel;

  RemoteAgentService(this.\_channel) {  
    final acpStream \= AcpStream.fromChannel(\_channel);  
    \_client \= ClientSideConnection(acpStream);

    \_client.onSessionUpdate((SessionUpdateParams params) {  
      // Dispatches streaming tokens, thoughts, and tool call events to the UI state  
      AgentStateBus.instance.handleUpdate(params);  
    });  
  }

  Future\<void\> sendUserPrompt(String sessionId, String textPrompt) async {  
    await \_client.prompt(  
      PromptRequest(  
        sessionId: sessionId,  
        content: \[TextContent(text: textPrompt)\],  
      ),  
    );  
  }  
}

The application state architecture relies on reactive state management (flutter\_bloc or Riverpod) to process incoming stream notifications without causing UI thread jank7. When AntiGravity streams responses over ACP via session/update notifications, the app appends text chunks to active markdown widgets (flutter\_markdown), renders structured collapsible cards for agent reasoning thoughts, and formats code diff blocks4.  
When AntiGravity attempts to execute terminal commands or write files on the host laptop, ACP triggers a session/request\_permission RPC request1. The host daemon forwards this frame over the WebSocket connection, causing the Flutter application to raise a system notification and pop up an authorization modal1. The user can review the exact command string or file modification path and select Approve or Deny, which transmits a JSON-RPC response back through the host proxy to unblock the agent execution loop in Zed1.

| Mobile Interface Component | Data Protocol Endpoint / Source | Target Interaction & Capabilities |
| :---- | :---- | :---- |
| **Agent Chat Stream** | ACP session/update stream7 | Displays token-by-token message chunks, agent thoughts, and code outputs10. |
| **Tool Approval Dialog** | ACP session/request\_permission \[cite: 1, 7, 8\] | Intercepts permission requests for terminal execution or disk modifications1. |
| **Prompt Input Bar** | ACP session/prompt \[cite: 7, 8, 13, 20\] | Formats and transmits user instructions, images, or contextual references20. |
| **Git Management Panel** | Custom Daemon JSON-RPC (/git/\*) | Surfaces uncommitted file diffs, stages changes, accepts commit messages, executes pushes. |
| **System Telemetry Bar** | Custom Daemon JSON-RPC (/system/\*) | Displays real-time laptop battery life, resource usage, and host process status. |

## **Protocol Messaging Specifications and Configuration**

To maintain consistency across the desktop stdio boundary and the mobile WebSocket connection, all messaging must conform strictly to the ACP JSON-RPC 2.0 specification1. The system uses standardized request and notification frames to orchestrate agent sessions8.

### **Session Initialization (initialize)**

During initial transport setup, the client negotiates protocol capabilities with the agent8. The initialize request establishes supported protocol versions and defines feature sets such as file system access or terminal execution support8.

JSON  
{  
  "jsonrpc": "2.0",  
  "id": 1,  
  "method": "initialize",  
  "params": {  
    "protocolVersion": 1,  
    "clientCapabilities": {  
      "fs": {  
        "readTextFile": true,  
        "writeTextFile": true  
      },  
      "terminal": true  
    }  
  }  
}

### **Response Streaming Notification (session/update)**

As AntiGravity processes prompts, it streams real-time state changes, thoughts, and text output to the client via one-way session/update notifications7.

JSON  
{  
  "jsonrpc": "2.0",  
  "method": "session/update",  
  "params": {  
    "sessionId": "sess\_987654321\_alpha",  
    "update": {  
      "sessionUpdateType": "agent\_message\_chunk",  
      "content": {  
        "type": "text",  
        "text": "Updating dependency definitions in Cargo.toml..."  
      }  
    }  
  }  
}

### **Action Authorization Interception (session/request\_permission)**

When an agent tool requires user permission before making file modifications or running system commands, it sends a session/request\_permission request, pausing execution until a matching response frame is returned1.

JSON  
{  
  "jsonrpc": "2.0",  
  "id": 42,  
  "method": "session/request\_permission",  
  "params": {  
    "sessionId": "sess\_987654321\_alpha",  
    "toolCall": {  
      "toolCallId": "call\_007\_exec",  
      "name": "terminal/create",  
      "parameters": {  
        "command": "cargo check \--all-targets"  
      }  
    }  
  }  
}

### **End-to-End Execution Sequence**

The operational lifecycle for remote control spans process setup, message routing, interactive approval, and version control synchronization:

> 1. **Process Spawning**: Zed initializes zed-remote-daemon as an ACP custom agent, which in turn launches the AntiGravity process and attaches asynchronous pipes to its stdin and stdout5.  
> 2. **WebSocket Connection**: The Flutter application connects to zed-remote-daemon over Tailscale TLS, authenticating via JWT pre-shared token9.  
> 3. **Session Interception**: When a user enters a prompt in Zed or on the mobile phone, the daemon assigns a session ID, routes the session/prompt frame to AntiGravity, and broadcasts the event over the WebSocket channel7.  
> 4. **Real-time Streaming**: AntiGravity emits session/update notifications containing text chunks and thought blocks7. The daemon forwards these frames simultaneously to Zed's local UI and the Flutter application7.  
> 5. **Tool Permission Handling**: If AntiGravity requests command execution via session/request\_permission, the daemon holds the response pending user approval1. The mobile user receives a modal prompt in Flutter, taps Approve, and the daemon returns the JSON-RPC response to AntiGravity1.  
> 6. **Out-of-Band Version Control**: The mobile user opens the right-hand panel in Flutter, views modified files, enters a commit message, and triggers Git commit and push routines executed directly by the daemon16.

## **Fault Tolerance, State Synchronization, and Security**

Because remote operations rely on mobile networks, the architecture must handle intermittent connectivity, process crashes, and session conflicts gracefully9.

### **Network Reconnection and Session Reconstitution**

Mobile devices frequently lose network coverage when transitioning between cellular towers or Wi-Fi networks9. To prevent state loss, the host daemon maintains a rolling event log in append-only JSONL files for every active session ID21.  
When the Flutter app reconnects after an outage, it issues a session/load request containing the active sessionId8. The host daemon reads the JSONL event log and replays missed session/update notifications back to the app, restoring the complete conversation history without disrupting the agent process running on the host laptop8.

### **Concurrency Control and Lock Resolution**

A potential conflict arises if a user attempts to issue prompts simultaneously from the desktop Zed editor and the mobile Flutter application. To prevent protocol state corruption, the host daemon enforces a strict single-writer mutex lock per session ID:

> * **Active Lock**: When a session/prompt request is processing, the daemon locks the prompt input stream for that session8.  
> * **Busy Rejection**: If a secondary prompt request arrives from another client while the lock is active, the daemon immediately returns a JSON-RPC error frame (-32001 Server Busy) to the secondary client, keeping the primary execution queue orderly8.

### **Host Security and Access Boundaries**

Leaving a laptop unattended in a remote location requires strict security boundaries to prevent unauthorized execution:

> * **Transport Security**: Restricting WebSocket interfaces to Tailscale private overlay IPs blocks external port scanning and localized network attacks on open hostel Wi-Fi networks9.  
> * **Permission Guardrails**: Daemon configuration flags allow users to set global safety rules (e.g., ACP\_PERMISSION\_MODE=acceptEdits), allowing harmless file modifications while mandating manual approval for destructive terminal commands (rm, sudo, or system formatting)6.

## **Strategic Implementation Roadmap**

Implementing this remote control infrastructure involves four progressive phases spanning proxy development, network setup, mobile application engineering, and end-to-end integration.

### **Phase 1: Host Proxy Daemon Engineering**

> 1. Create a Rust binary project using tokio, serde\_json, and tokio-process libraries16.  
> 2. Implement the stdio interception proxy that spawns the AntiGravity CLI as a child process and pipes standard input and output streams17.  
> 3. Build an NDJSON framing engine that parses raw streams into typed JSON-RPC 2.0 ACP structures7.  
> 4. Implement local JSONL file logging to persist session state history21.

### **Phase 2: Secure Mesh Networking and Command Engines**

> 1. Integrate tokio-tungstenite and rustls to serve encrypted WebSocket connections over a Tailscale private IP address9.  
> 2. Implement JWT token authentication for incoming WebSocket handshake requests.  
> 3. Build the Git automation module wrapping git2 bindings and std::process::Command calls for staging, committing, and pushing code16.  
> 4. Implement system management routines to capture hardware metrics and trigger system power state changes17.

### **Phase 3: Mobile Client Development in Flutter**

> 1. Initialize a Flutter project and add the acp\_dart package dependency7.  
> 2. Construct the dual-panel mobile interface:  
   * **Agent Panel**: Builds a chat thread rendering streaming markdown, collapsible thought cards, and interactive approval modals1.  
   * **Control Panel**: Displays file modification lists, diff previews, commit fields, sync buttons, and system metrics widgets.  
> 3. Implement WebSocket reconnection logic with auto-retry and state replay handling9.

### **Phase 4: Zed Configuration and System Validation**

> 1. Register zed-remote-daemon in Zed's global settings.json under agent\_servers5.  
> 2. Launch a local agent thread in Zed to verify transparent stdio proxying1.  
> 3. Connect the Flutter app over a mobile network via Tailscale, execute remote prompts, approve tool calls, and complete Git commit/push workflows1.

## **System Synthesis and Operational Conclusions**

The combination of Zed's open architecture, the Agent Client Protocol, and a custom host proxy provides a powerful foundation for remote development workflows1. Rather than attempting to mirror a heavy graphical code editor across small mobile screens, isolating the protocol stream decouples reasoning and system management from visual layout constraints4.  
By positioning a Rust-based interception daemon between Zed and the AntiGravity agent, developers can stream conversation threads, authorize terminal execution, manage version control state, and control laptop power settings remotely from a smartphone6. This approach delivers complete operational control over remote development environments, ensuring host machines remain productive, secure, and accessible from anywhere4.
